# Unauthorized student profile disclosure via `GET /api/usuarios/{id}`

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-09-06 21:58:46 UTC
**Target:** backend/tcc-backend
**Endpoint:** /api/usuarios/{id}
**Method:** GET
**CWE:** CWE-862
**CVSS:** 4.3
**Fix Effort:** Low

## Description

A low-privilege authenticated student can retrieve another student's profile by ID. The response includes private account and academic metadata such as email, RA, semester, interests, institution, and preferences without any ownership check.

## Evidence

Authenticated as a different student, the profile endpoints returned another user's data:

```http
GET /api/usuarios/2 HTTP/1.1
Authorization: Bearer <alice-token>
```

```http
HTTP/1.1 200 OK
{
  "id": 2,
  "nome": "ALUNO bob",
  "email": "aluno-bob@teste.com",
  "tipo": "ALUNO"
}
```

```http
GET /api/usuarios/2/perfil HTTP/1.1
Authorization: Bearer <alice-token>
```

```http
HTTP/1.1 200 OK
{
  "id": 2,
  "email": "aluno-bob@teste.com",
  "ra": "RABOB",
  "tema": "sistema",
  "notificacoesAtivas": true
}
```

The write path is blocked, confirming the issue is specific to unauthorized reads:

```http
PUT /api/usuarios/2 HTTP/1.1
Authorization: Bearer <alice-token>
```

```http
HTTP/1.1 403 Forbidden
{
  "message": "Voce nao pode editar outro usuario"
}
```

## Impact

An authenticated student can read another student's restricted profile data by guessing or enumerating the user ID. In the validated request, the response disclosed the victim's email and `RA`/profile fields, enabling cross-account privacy leakage and user enumeration.

## Technical Analysis

`UsuarioService.validarAcessoAoUsuario()` returns early for any target whose `tipo` is `ALUNO`, so `findById()` and `findProfileById()` do not bind the caller to the object being requested. As a result, any authenticated user can read another student's record through `GET /api/usuarios/{id}` and `GET /api/usuarios/{id}/perfil`. The same helper is also reused by `findProjetosByUsuario()`, so the broken authorization decision affects additional user-linked reads as well.

## Proof of Concept

1. Register two student accounts and one authenticated low-privilege session.
2. Log in as student A.
3. Request `GET /api/usuarios/{studentBId}` and `GET /api/usuarios/{studentBId}/perfil` with student A's token.
4. Observe that both requests return `200 OK` and expose student B's email and profile fields.
5. Send `PUT /api/usuarios/{studentBId}` with student A's token to confirm the write path is still blocked and the issue is limited to unauthorized reads.

## Remediation

Restrict `UsuarioService.validarAcessoAoUsuario()` so that cross-user reads are allowed only for explicitly authorized roles and relationships. At minimum, require the caller to be the same user, an administrator, or an orientador when student records are intentionally visible; add regression tests for both `GET /api/usuarios/{id}` and `GET /api/usuarios/{id}/perfil` to ensure another student receives `403 Forbidden`.

## Assumptions

Assumes an authenticated low-privilege student can obtain another user's numeric ID; the application returns user IDs in normal responses and uses the same identifier across profile routes.
